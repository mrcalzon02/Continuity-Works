Java decision authority adapter
-------------------------------
modules/continuityworks-api now includes ContinuityWorksDecisionAuthorityAdapter as a thin transport-facing authority around a configured ContinuityWorksCompactBlueprintApi provider. It deliberately delegates API version reporting, decision-profile discovery, begin, next, apply, validate, and finalize operations through the configured provider instead of reimplementing mutator vocabulary, dependency semantics, validation, or finalization.

The adapter adds transport-safe expected-revision checking before mutation application. Late asynchronous inference output that targets an older decision revision fails closed with a stale-revision error, while the authoritative immutable state returned by the provider remains the state of record. This gives a future HTTP/IPC/companion transport a stable Java authority seam without creating a second decision engine.

The existing tests/test_blueprint_decision_chain_java.py Java 17 harness was extended rather than creating a parallel test framework. It compiles every Java source under modules/continuityworks-api, instantiates the authority adapter over a minimal ContinuityWorksCompactBlueprintApi provider, verifies provider API/protocol delegation, verifies immutable revision advancement, verifies stale revision rejection, verifies delegated validation, and verifies delegated finalization.

Delegated HTTP decision bridge
------------------------------
The existing Python HTTP/publication server contains a non-duplicative conditional bridge for the Java decision-chain contract. The bridge exposes the route family only when CONTINUITY_WORKS_DECISION_AUTHORITY_URL names a separate authoritative decision service:
- GET  /v1/blueprints/decision/profile
- POST /v1/blueprints/decision/begin
- POST /v1/blueprints/decision/next
- POST /v1/blueprints/decision/apply
- POST /v1/blueprints/decision/validate
- POST /v1/blueprints/decision/finalize

The Python service does not implement, reinterpret, or persist decision semantics. It forwards configured calls to the authoritative service. With no authority configured, the routes are omitted from OpenAPI and machine discovery and direct calls fail closed with decision_authority_unavailable. A self-referential authority URL is rejected with decision_authority_loop so the service cannot accidentally recurse into itself. The configured authority address is not disclosed through health/discovery metadata. Timeout and URL validation remain bounded at the bridge boundary.

Regression coverage in tests/test_server.py covers both states: unconfigured authority remains unadvertised/fail-closed, while a configured authoritative test double causes the six routes to appear in OpenAPI and discovery and receives profile/apply requests unchanged. The bridge remains accepted at source/local-harness/repository-suite level, but no claim is made that the configured Render service currently has a Java authority process attached or that these decision routes execute remotely.
