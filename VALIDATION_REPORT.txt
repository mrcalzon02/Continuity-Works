Delegated HTTP decision bridge
------------------------------
The existing Python HTTP/publication server now contains a non-duplicative conditional bridge for the Java decision-chain contract. The bridge exposes the route family only when CONTINUITY_WORKS_DECISION_AUTHORITY_URL names a separate authoritative decision service:
- GET  /v1/blueprints/decision/profile
- POST /v1/blueprints/decision/begin
- POST /v1/blueprints/decision/next
- POST /v1/blueprints/decision/apply
- POST /v1/blueprints/decision/validate
- POST /v1/blueprints/decision/finalize

The Python service does not implement, reinterpret, or persist decision semantics. It forwards configured calls to the authoritative service. With no authority configured, the routes are omitted from OpenAPI and machine discovery and direct calls fail closed with decision_authority_unavailable. A self-referential authority URL is rejected with decision_authority_loop so the service cannot accidentally recurse into itself. The configured authority address is not disclosed through health/discovery metadata. Timeout and URL validation remain bounded at the bridge boundary.

Regression coverage was added in tests/test_server.py for both states: unconfigured authority remains unadvertised/fail-closed, while a configured authoritative test double causes the six routes to appear in OpenAPI and discovery and receives profile/apply requests unchanged. The exact committed bridge source was also exercised in an isolated local HTTP behavior harness: unconfigured profile returned 503, configured profile and apply were delegated successfully, and self-loop configuration returned 503. Python AST parsing of the bridge and regression-test source passed before repository writes.

This is source/isolated-harness evidence, not a full repository validation run. No claim is made that the configured Render service currently has a Java authority attached or that these decision routes are live on the internet.
